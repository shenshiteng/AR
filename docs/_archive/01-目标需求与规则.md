## 一、原始目标（2026-10-20 起点）

### 1.1 最初那句话

> **在走廊/门口贴二维码 → 扫码 → 页面告诉你"你在这里" → 选要去的实验室 → 画出路线 + 分步文字指引（支持多栋楼、跨楼层）。**

约束同时定死：**不用装 App、不用后端**。

### 1.2 用户给的项目背景（决定了所有技术选型）

日志 2026-10-20「待办/下一步」里记着用户当时交代的实际情况：

| 条件 | 对设计的影响 |
|---|---|
| **多栋楼** | 数据结构从一开始就要有 `buildings[]` + `links[]`（跨楼 `outdoor`） |
| **规模较大** | 必须有批量生成二维码的工具，不能一个个人工画 |
| **已有平面图图片** | 坐标系直接用图片像素坐标；图片留空时才退化为示意图 |
| **只做查询端** | 不做管理后台、不做录入界面（后来补了 `marker.html`/`import.html` 也只是本地工具） |

这四条至今没变，是判断"某个新需求是否在项目范围内"的基准。

### 1.3 两条并行的目标线

项目实际是**两条线并行**推进的，很容易混淆，必须分清：

| 线 | 目标 | 代表产物 | 定位方式 |
|---|---|---|---|
| **A. 网页扫码导航** | 扫码即定位、看整张地图和完整路线 | `index.html` → `fp-ar.html` | **二维码**（带 `?loc=` 参数） |
| **B. AR 极简导航** | 对准标记码扫一下 → 大箭头 + 一句话指引 | `ar.html` → `fp-ar.html` | **ArUco 码**（纯几何，靠 ID 反查） |

**两条线在 2026-11-11 合流**：因为扫 QR 与扫 ArUco 最终都落到同一个 `doLocate()`，朝向都算 `normal+180`，
所以决定**去掉 ArUco、只贴 QR**（见第五章）。

## 三、需求背后的判断标准（用户怎么算"对"）

从 62 条需求里能提炼出用户的验收口味，这些比具体需求更重要：

| 标准 | 出处/表现 |
|---|---|
| **要"真的"，不要"看起来像"** | 楼梯必须真踩台阶真抬升；跨层必须真走楼梯不能瞬移 |
| **默认安静** | 没选目的地就不许显示指引；URL 参数只许预填，不许抢跑 |
| **一份数据一个出处** | 同一份几何被页面和渲染各算一遍必然漂移，必须统一 |
| **宁可报不通，不许偷偷绕** | "兜底换面"是寻路的万恶之源 |
| **视觉产物要站在用户实际站的位置验证** | 不是随便 teleport 一个角度截图就算通过 |
| **点名才改，没点名别动** | "拆墙"只拆点名那处；用户说"补上"就是全撤 |
| **代码要讲人话** | 用户是编程新手，要给能直接跑的代码 + 说明改哪个文件怎么验证 |
| **一次只做一步** | 不提前准备下一步、不提前逼用户拍板 |

## 四、硬规则清单（不可违反）

以下规则都由用户明确拍板或由血的教训固化，改动前必须先读。

### 4.1 技术栈与代码风格

| 规则 | 说明 |
|---|---|
| 纯前端原生 JS | 无框架、无打包器 |
| ES5 风格 | IIFE 包裹 + `'use strict'` + `var` + `window.X` 全局 + 中文块注释 |
| 数据走 `<script src>` | 不用 fetch，保证 `file://` 双击也能跑 |
| 数据唯一事实源 | `data/labs.js`（`window.LAB_DATA = {...}`），本质是「JSON 穿 JS 马甲」 |
| `labs.js` 格式极严格 | **不能有注释、不能有尾逗号、字符串必须双引号**；改完用 `python tools/export_map_data.py` 跑通即语法合法 |

### 4.2 全局命名冲突（踩过，必守）

第三方库 `js-aruco2` 的全局对象叫 **`AR`**。页面脚本里**绝不能再定义 `var AR`**
（曾把桥接模块命名 AR，遮蔽识别库 → 扫码报"识别库没加载"）。桥接模块现名 `Nav`（页面内）/ `window.__AR__`（全局）。

**已占用全局名单（新起变量名前先 grep）**：
```
THREE / AR / LAB_DATA / FLOOR_* / FPWorld / FPView / FPInput / FPValidate /
LabRouter / ArucoMark / __FP__ / __AR__ / __arDebug
```
注意 `AR`（识别库）与 `__AR__`（自有桥）差一个下划线，极易混。

### 4.3 数据结构约定

- 顶层：`site` / `metersPerPixel` / `buildings[]` / `floors[]` / `links[]` / `labs[]` / `locations[]`
- `floors[]`：`{ id, building, name, image, mapImage, width, height, nodes[], edges[], rooms[] }`
- `nodes`：`{ id, x, y, note }`，**id 约定 `楼层ID/n序号`**（如 `B2-4/n1`）；
  坐标 = 图片像素，原点左上，x 向右、y 向下
- `edges`：`["n1","n2"]` 或带第三项手动米数；**同层可简写**，程序自动补楼层前缀（`router.js:34-36`）
- `rooms`：`{ id, name, x, y, w, h, kind, area?, desc?, tags? }`
  kind 字典：lab/office/room/store/service/toilet/stair
- `labs`：`{ id, name, floor, room, door, tags, desc?, phone? }`；`door` 指向走廊节点
- `locations`：`{ id, floor, node, place, marker, normal }`
- **`normal` 方位约定：0=东、90=南、180=西、270=北**（图上方为北）
- `metersPerPixel` 是**声明估值**（当前 0.045，图上无比例尺可溯源）；
  「约 X 米」数量级对即可，**别对外说精确**

### 4.4 朝向与坐标

- 朝向 `theta` 约定：**0=东(+x)、90=南(+y)、180=西、270=北**（顺时针，与 `locations.normal` 一致）
- 扫码定位朝向 = `normal + 180°`（人总是面朝贴纸站）
- **只用罗盘的增量，不用绝对值** —— 室内钢结构/配电箱/管道让罗盘偏 30~90°（实测这栋楼偏约 80°），
  但"转了 90°"这个变化量是准的，做差就抵消
- 罗盘脏数据处理：单帧跳变 > 45°/120ms 直接丢弃；连续读数低通平滑

### 4.5 第一人称键位（2026-11-05 用户最终拍板）

| 键 | 作用 |
|---|---|
| W / S | 前进 / 后退（**只位移，绝不转向**） |
| **A / D** | **左转 / 右转视角** |
| ← / → | 同样是转身 |
| Shift + ←/→ | 平移 |

**最高优先级**：页面 loop 里任何 fwd/back/turnL/turnR/strafe 输入**立即中断自动巡航**
（`autoNodes=null; climb=null`），提示「已由键盘接管」。

### 4.6 楼梯（双跑折返）五条硬规则

1. **换层只认"上一层地面"**：`checkStairTransition` 阈值是 `|z| ≥ 层高−0.02`。
   半层高(1.5m)是**中间平台**，那里只转弯、绝不换层。
2. **平台转弯的目标角必须每帧按当前位置重算**。锁死一次会出现"已转到位但永不满足放行"的原地死锁。
3. **坡度参数化按"可走范围"归一**，不是房间矩形：`pad=min(20, L*0.25)`、`buf=min(10, span*0.3)`。
   按矩形算的话，60~70px 的小楼梯间永远走不到平台。
4. **一份几何只留一个出处**：`axis/dir/pad/buf/plat` 全放 `world.stairs`（fp-core 生成），
   高度场 / 3D 台阶 / 页面转弯判定全部读它。谁再自己"猜门在哪一侧"必然漂移。
5. **门侧用跨层边上的楼梯口节点判定**（`buildWorld` 传 `stairDoors`）。
   用"离房间中心最近的路点"会判错。另外窄楼梯间跑道中心要夹 `LANE_MARGIN=24`，否则换道会把人挪进墙里卡死。

### 4.7 墙数据与清理（2026-11-05 用户拍板最终版）

1. **闭运算合并平行细线**（close-cells=1，合并间隔 ≤8px）——消灭第一人称里的「平行栅栏」
2. **只删房间矩形深处的墙**（interior-margin-px=8）
3. **路网保路**：nodes+edges 连了边的走廊，边线两侧 `corridor-half-px=12px` 内的墙格一律挖掉
   ——「数据说能走就保证不挡」
4. 判定墙的准绳：**真实墙 = 房间框边线 + 楼外轮廓；房间内部与走廊中间的细条多是照片噪声**
5. **教训**：曾试「edge-band 只留走廊两侧+房间轮廓」的激进版，把承重/必要墙也删了，**被用户否掉**

### 4.8 三维沙盘（nav3d）

- 源码模板 `nav3d/_dev.html`，成品 `nav3d/index.html`；
  **改 `_dev.html` 后必须重跑 `tools/build_single.py`**
- 数据：`nav3d/data/floor-3f.js`（**手写，唯一事实源**）；
  `floor-2f.js`/`floor-5f.js` 由 `tools/gen_floors.py` 派生，**勿手改**
- **★ 派生楼层不能整段复制「楼体核心」**（血泪教训）：五楼最初 `dict(by_id['STAIR-NW'])` 抄三层的楼梯/厕所，
  结果楼梯占了厕所位置、501 和东端楼梯上下互换 —— 因为**各层板的楼梯/厕所在哪一排、门朝哪可能完全不同**。
  房名里带"门朝东""服务台旁"这种残留就是抄串了的信号。
- `check_grid.py` 的路网模型：**楼板只存在于 corridors+spurs 上**，其余全挡；
  房间靠"门点外 44px 落在走廊里"判通 → **走廊必须盖住每个门点**

### 4.9 寻路的死规矩

- **"兜底换面"是寻路的万恶之源**：宁可报"不通"，也不要偷偷换一条不该存在的路
- **"默认全图可走"的栅格在小场景看着能用，一到大图就到处穿墙**：楼板必须显式定义（只挖走廊）
- 改了门/墙方向，**一定要回头看 `perimeter` 里有没有同一条线**（假外墙不挡寻路，只挡眼睛）
- 验证要有**独立第三方校验**（`check_grid.py`）+ **运行时自证**（`?probe=`），光看截图不可靠

### 4.10 协作与交付

- **数据共享、页面隔离**：`data/labs.js` 改动所有对话框同步；
  但做出来的 html 页面是隔离的（本线负责 `fp-ar.html` + `nav3d/index.html`，`fp.html` 不是本线的页面）
- **一次只做一步**，不提前准备下一步、不提前逼用户拍板
- **讲人话、给能直接跑的代码**、说明改哪个文件怎么验证（用户是编程新手）
- **主动记错、避免重犯**（每次明显失误立即记入当日日志或 `MEMORY.md`）
- 生成视觉产物前**先问清样式**（白边大小、是否加文字标注），别凭感觉批量生成
- 自检要验**最终产物**本身（SVG 对不代表 PNG 对；产物链每一环单独验）

### 4.11 环境与工具链坑（本机特有）

- **本机 `pip` 和 `python` 是两个解释器**，装包必须 `python -m pip`
- **`.bat` 必须存成 GBK**：本机 cmd 代码页 936，UTF-8 写含中文的 bat 会被按字节当命令执行
  → **bat 里只写 ASCII 输出，文件存 GBK**
- **Chrome 无头截图必须用绝对 Windows 路径**，相对路径报"拒绝访问 (0x5)"
- 无头 Chrome 要 WebGL 必须加 `--enable-unsafe-swiftshader --use-angle=swiftshader`
- 本地 http 页跳 https 时 `--virtual-time-budget` 不退出会卡住 → 分段验证
- 手机真机摄像头**必须 https**（安全上下文），`http://192.168.x.x` 直接被拒
- 本机没有全局 `node`；DSH 自带 node 在
  `C:\Users\35391\.dsh\dsh-runtimes\dsh-next-primary-runtime\dependencies\node\bin\node.exe`

## 五、关键架构决策（为什么是现在这个样）

| 决策 | 理由 |
|---|---|
| **纯静态、零后端** | 用户要"不用装 App、不用后端"；数据走 `<script src>` 所以 `file://` 也能开 |
| **地图 = 数据 + 渲染函数（"活地图"）** | 不是死图片。四层：数据层→绘制层→视图层(相机变换)→出口；图片退化为参考层 |
| **第一人称渲染用 three.js 真 3D** | 用户要"真的走"，r128 是最后一个带全局 `THREE` 的稳定版，离线内置 |
| **二维码与 ArUco 并存 → 最终只留二维码** | 两者都落到 `doLocate()`，朝向都算 `normal+180` → ArUco 冗余（2026-11-11 定调） |
| **加 `deploy/redirect` 跳转层** | `make_qr.py` 原会把 sharecode 写进码里，平台一重新发布就全废。加跳转层后 sharecode 只在一个常量里，改它不用重印 |
| **每点位一张码 + 点位 ID 冻结** | 取舍明确选了「扫码即知位置」，放弃"单一永久码"路线（单一码换不来扫码即知位置） |
| **5 个楼梯口都是定位起点** | STAIR-NW/NE/E/SW/SE，门节点 n1/n28/n30/n14/n22，各配二维码（P-B2-01~05） |

### 5.1 关于"单一永久码"那条被放弃的路线

`docs/永久二维码方案.md` 里论证得很完整（三层结构：码 → 稳定入口 → 302 跳转 → 当前应用），
但它的结论是：**单一码天然换不来"扫码即知位置"**。
2026-11-11 用户明确选了另一边：**扫码即知位置 → 每点位一张 + 点位 ID 冻结**。
这两件事不能同时要，这是项目里最明确的一次取舍。

### 5.2 关于"双码方案"（大 ArUco + 小 QR）

`docs/ArUco扫码导航上线方案.md` 曾论证必须双码（ArUco 没有二维码的三个定位角，通用扫码器全都是认不出的）。
但 2026-11-11 的实践推翻了这个必要性判断：既然 `?loc=` 已经能做到扫码即定位，
ArUco 能提供的唯一额外信息（"我在哪个楼梯口"）用 QR 也能给，且更省事。
**所以双码方案被"只贴 QR"取代**，那份文档现在应作为历史论证材料读，不是施工依据。
