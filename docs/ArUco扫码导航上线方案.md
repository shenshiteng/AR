# 第二实验楼 · ArUco 扫码导航 上线方案

> 适用范围：第二实验楼 2 层 / 3 层 / 5 层
> 现状：`fp-ar.html` 已上线，12 个楼梯口定位码已生成，104 间实验室已建模
> 本文档解决三件事：**为什么要两个码、牌怎么印怎么贴、学生怎么用**

---

## 一页结论

| 问题 | 结论 |
|---|---|
| 只贴 ArUco 行不行 | **不行**。ArUco 没有二维码的三个定位角，微信扫一扫、苹果相机、安卓扫码全都认不出。必须有第二张能被通用扫码器识别的码 |
| 那怎么做 | **一张牌两个码**：上面大 ArUco 管定位（进页面后扫），下面小二维码管进站（微信扫） |
| 做小程序还是 APP | **小程序**。APP 要下载安装，校园里没人会为一个找路功能装 App |
| 码印多大 | 楼梯口 A4 牌：ArUco 120mm + 入口码 45mm；门牌 A5：ArUco 80mm + 入口码 40mm |
| 最该先做什么 | ① 修「进页面自动扫」这一处 ② 印 12 张 A4 牌贴上去，4 台手机实测 |

**一句话**：现在这套东西学生用不起来，不是因为码贴得不够醒目，而是因为**扫完 ArUco 页面没反应**——这个必须先修，否则贴多少张都白贴。

## 第一章 为什么必须是两个码

### 1.1 ArUco 和二维码不是同一类东西

| | 普通二维码 | ArUco 码 |
|---|---|---|
| 结构 | 33×33 以上模块 + 三个角的定位方块 | 5×5 黑白格 + 一圈等宽黑边 |
| 谁认得出 | 微信、支付宝、苹果相机、安卓系统扫码、各类扫码 App | **只有你自己页面里的 `js-aruco2`** |
| 里面能放什么 | 文字、网址（可跳转） | 一个 0–1022 的编号 |
| 扫完会怎样 | 跳转网页 / 显示内容 | 什么都不会发生 |

关键在**定位角**。二维码靠左上、右上、左下三个大方块，扫码器先找到它们才能摆正画面、再解内容。ArUco 全身是均匀的黑白格子，没有任何一个角落长得特殊，通用扫码器根本不知道从哪开始读。

### 1.2 所以「扫描」在这个系统里是两段

```
第一段：进站          第二段：定位
微信扫一扫           页面里对准
    ↓                    ↓
 普通二维码           ArUco 大码
    ↓                    ↓
 打开 fp-ar.html      知道你在哪个楼梯口
```

**小码负责「进得来」，大码负责「知道你在哪」。** 两件事，缺一不可。

### 1.3 为什么入口码不带位置参数

页面支持 `?loc=P-B2-03` 这种写法，扫了直接定位到东南楼梯口。看起来只要把 12 张入口码分别带上不同的 `loc`，扫一次就完事，还要 ArUco 干什么？

原因是代码里两条路走的是同一段逻辑（`fp-ar.html:245` 的 `doLocate()`），朝向一律按 `normal + 180` 算。也就是说：

> **扫 ArUco 和扫一张带 `loc` 的二维码，系统里得到的结果完全一样。**

如果入口码带上 `loc`，ArUco 就变成纯装饰了。所以本方案的选择是：

- **入口码全楼统一一张图案，不带 `loc`** → 定位这件事交给 ArUco，它才有存在价值
- 附带好处：以后换域名、换点位，入口码的**图案**不用重新设计排版，只是底下的地址换了；而 12 张 ArUco 码一张都不用动

> 如果你就想「扫一次完成」，第二章 2.6 给了取舍。

## 第二章 牌怎么印（施工核心）

### 2.1 一条公式定尺寸

ArUco 能扫多远，取决于**码印多大**。原因是页面检测时会把画面**缩到 340 像素宽**再送进识别器（`fp-ar.html:452`），码在画面里必须占到足够比例才认得出。

实测推算：

> **ArUco 码面宽度 ≈ 扫描距离 × 0.2**
> 反过来：**能扫的距离 ≈ 码面宽度 × 5**

| 码面宽度 | 能扫到的距离 | 够不够用 |
|---|---|---|
| 53mm（现在打印出来的尺寸） | **27cm** | 手机得贴到墙上，不可用 |
| 80mm | 40cm | 门牌够用 |
| 120mm | **60cm** | 楼梯口够用 |
| 145mm（A4 能放的极限） | 72cm | 更好 |
| 205mm（A3 能放的极限） | 1.02m | 远距离也认得出 |

现在的码印出来只有 53mm，因为 `aruco/print.html` 把 1020 像素宽的图排成 130mm，里面 420 像素的黑框码面折算是 53mm。**这是目前最需要改的一个数字。**

### 2.2 A4 楼梯口牌（12 张）

竖版，页边距 12mm，可用区域 186 × 273mm。

| 从上到下 | 内容 | 高度 |
|---|---|---|
| ① | 「扫码定位」大字 + `3层 · 东南楼梯口` | 30mm |
| ② | **ArUco 码面 120mm**（含静区实占 154mm） | 154mm |
| ③ | 留白 | 8mm |
| ④ | **入口二维码 45mm** + 两行说明 | 60mm |
| ⑤ | 点位编号 `P-B2-03` | 15mm |
| | **合计** | **267mm**（余 6mm） |

**为什么 ArUco 只能做到 120mm 而不是 145mm：**
ArUco 四周必须留一圈纯白（专业叫「静区」），宽度至少等于一个格子。120mm 的码每个格子是 17mm，所以左右各要 17mm 白边，整块占 154mm 宽——已经吃掉 A4 大半。如果做到 130mm，整块就是 167mm 高，再加上 45mm 入口码和文字，总高会到 283mm，**超出 A4 的 273mm**，会被裁掉。

**入口码为什么是 45mm：**
入口地址约 70 个字符。用 Q 级纠错 + 4 模块静区后，二维码约 **45×45 模块**。45mm 时每个模块 1.0mm，手机在 **20cm 内**能稳定扫出。缩到 40mm 就只剩 0.89mm/模块，暗光或手抖时开始失败——**45mm 是 A4 牌的下限，不要再缩。**

> 注意一个反直觉的地方：把纠错从 M 提到 Q 会让码从 41×41 涨到 45×45 模块，同样 45mm 下每模块从 1.1mm 降到 1.0mm。所以如果实测扫不出，**优先把码放大到 50mm，而不是把纠错降回 M**——墙上会落灰、会翘边，冗余比模块大小更值得留。

### 2.3 A5 门牌（104 张）

竖版，页边距 10mm，可用区域 128 × 190mm。

| 内容 | 尺寸 |
|---|---|
| 房间号大字（如 `324`）+ 房间名 | 25mm |
| **ArUco 码面 80mm**（含静区实占 103mm） | 103mm |
| **入口二维码 40mm** + 一行说明 | 55mm |
| 合计 | **183mm**（余 7mm） |

80mm 的码能扫 40cm，而人站在门牌前通常是 30–50cm，刚好。

### 2.4 想更醒目就用 A3

A3（可用 267 × 390mm）能放 **205mm** 的 ArUco，扫描距离 1.02m，入口码可以放大到 60mm。

建议只用在**人流量最大的那个主楼梯口**，其余仍用 A4。A3 面积是 A4 的两倍，全楼 12 张都用 A3 的话墙面占用和成本都会翻倍。

### 2.5 牌面文字（照抄，共 5 行）

```
        扫码定位
     3层 · 东南楼梯口

   ┌─────────────────┐
   │                 │
   │    ArUco 大码    │   120mm
   │                 │
   └─────────────────┘

     ① 微信扫下方小码进入导航
        ┌───────┐
        │ 入口码 │        45mm
        └───────┘
     ② 进入后把「大方块」对准取景框

  扫不出？页面里选：3层 → 东南楼梯口   P-B2-03
```

> 第 ① ② 两行是全篇最容易漏、又最致命的。没有这两行，学生只会举着手机对着 ArUco 反复扫，然后说「你这个扫不出来」。

### 2.6 如果你就想扫一次完成（取舍）

把入口码做成 12 张不同的、各自带 `loc=P-B2-0x`，扫一次直接定位，ArUco 就只当墙面标识。

- 好处：学生少一步，成功率更高
- 代价：① ArUco 白做了；② 换域名时 12 张入口码全部重印（现在 ArUco 不用重印就是因为入口码统一）

**建议**：先按双码做，实测时两种都试，用实测数据决定。

### 2.7 入口码本身要改的 3 处（`tools/make_qr.py`）

| # | 现在 | 改成 | 原因 |
|---|---|---|---|
| 1 | 静区 `border=2`（2.4mm） | `border=4` | 规范要求 4 模块；现在边上稍微裁一点就扫不出 |
| 2 | 纠错等级用库默认 M（15%） | 显式写 `Q`（25%） | 墙上会脏、会翘边，需要更多冗余 |
| 3 | 每个点位循环、强制拼 `loc=` | 加一个开关，生成一张**统一入口码** | 现有脚本做不出「不带 loc」的码 |

> 待确认：如果托管平台允许关掉 `sharecode` 校验，地址能缩短到 30 字符左右，二维码从 45×45 降到 37×37 模块，同样 45mm 下每模块从 1.0mm 涨到 1.2mm（约 +20%），**扫码明显更容易**；同时码面还能缩回 40mm 省版面。这条要先去问平台。

## 第三章 做小程序还是 APP

### 3.1 先想清楚一件事

因为 ArUco 必须在**应用内**扫，所以「应用怎么打开」和「打开后怎么扫」是两个独立问题。这跟普通扫码导航不一样——普通导航扫一次就进去了，不用先有应用。

所以评判标准是两条：
1. **学生怎么进来**（第一次 / 第二次）
2. **进来后扫得顺不顺**（要不要点按钮、会不会一直扫）

### 3.2 三方对比

| | 微信小程序 | H5 网页（现状） | 原生 APP |
|---|---|---|---|
| 学生怎么进来 | 扫入口码一次，之后在微信「最近使用」里**一步打开** | 每次都要重新扫入口码 | App 图标点开 |
| 第一次成本 | 扫码 | 扫码 | **去应用商店下载安装** |
| 能否「举起来就认」 | **可以**，camera 可常驻自动扫，不用点按钮 | 需要先修，且受浏览器限制 | 可以 |
| 摄像头稳定性 | 微信统一授权，较稳 | 微信内置浏览器兼容性有坑（本项目至今**没有一条实测记录**） | 最稳 |
| 计步 / 屏幕常亮 | 现成接口，一行调用 | 要自己写，iOS 限制多 | 完全可控 |
| 开发量 | 要重写界面（但 2D 俯视图可复用，见下） | 已经做好了 | 最大，双端 |
| 上线门槛 | 主体注册 + ICP 备案 | **零门槛，已上线** | 双端上架审核 |
| 更新 | 后台发布，用户无感 | 改完即生效 | 每次发版等审核 |

**关于开发量，有个好消息**：`fp-ar.html` 并没有加载 three.js 的三维场景，实际只用 `fp-view.js` 里的 2D 俯视图绘制，AR 画面是 `<video>` + canvas 叠加。迁到小程序是：`<video>` 换成 `<camera>`、canvas 2D 绘制接口几乎逐行能用、`js-aruco2` 是纯 JavaScript 可以直接跑。**不是重写 3D 引擎。**

### 3.3 APP 为什么不推荐

- 校园找路是**低频**行为，一学期可能用三五次。为这个装一个 App，绝大多数人不会装
- iOS 要开发者账号（个人 99 美元/年，企业 688 元/年），安卓要过各家应用商店审核
- 每次改文案都要重新发版
- 唯一的优势是摄像头和传感器完全可控——但小程序已经够用了

**只有一种情况该做 APP**：将来要上蓝牙信标做室内米级定位，或者要离线地图。现在不需要。

### 3.4 路线 A：学校主体小程序（推荐）

| 项目 | 内容 |
|---|---|
| 需要材料 | 事业单位法人证书或营业执照、对公账户、管理员身份证 |
| 流程 | 注册 → 微信认证（300 元/年）→ **ICP 备案（7–15 个工作日）** → 选类目 → 开发 → 提审 |
| 建议类目 | 工具 → 信息查询；或 教育 → 教育信息服务 |
| 名字 | 可以正常写「第二实验楼导航」 |
| 能用的能力 | `camera` 组件 + 实时帧、罗盘、计步、屏幕常亮、批量生成带参数的小程序码 |

**注意**：`camera` 组件的「扫码模式」只认二维码和条码，**不认 ArUco**。要扫 ArUco 必须用实时帧接口（`onCameraFrame`）把画面喂给 `js-aruco2`。这个接口在部分安卓机型会返回空帧，iOS 上帧率只有 10–15 帧/秒。**这是小程序方案唯一的重大技术风险，必须先在真机上验。**

### 3.5 路线 B：个人主体小程序（备选）

主体办不下来时可用，但有三条硬约束：

1. **类目只能选工具类**（工具-效率 / 工具-查询），别选教育类——教育类要办学资质
2. **必须去机构化**：小程序名称、图标、页面里不能出现校名、校徽、「学校」「学院」字样，否则大概率被判「需教育资质」而驳回
3. **同样要 ICP 备案**，个人备案 7–15 个工作日；同一身份证最多注册 5 个小程序

**好消息**：本项目不需要微信支付、不需要获取手机号、不需要 URL Scheme，个人主体这三个短板都用不上。

### 3.6 推荐路线：三阶段，每阶段有明确的停/走判据

| 阶段 | 时间 | 做什么 | 继续的条件 | 停下的条件 |
|---|---|---|---|---|
| 第 0 阶段 | 本周，零成本 | 重排码号 → 印 12 张 A4 双码牌 → 贴 → 4 台手机实测 | 至少 3 台能「扫小码进站 + 60cm 认出大码」 | 微信内摄像头普遍打不开 → 直接跳小程序，别在 H5 上耗 |
| 第 1 阶段 | 1–2 个月 | 主体批下来 → 小程序 v1（重点做「常驻自动扫」） | 真机 `onCameraFrame` 能拿到可用帧 | 安卓普遍空帧 → 退回 H5 + 固定入口 |
| 第 2 阶段 | — | 主体办不下来 → 个人主体小程序（去机构化命名） | — | — |

**不要跳过第 0 阶段直接开发小程序。** 因为如果 60cm 都认不出，小程序做出来一样认不出——问题在码的尺寸和检测分辨率，不在平台。

## 第四章 怎么贴才扫得到

### 4.1 位置与高度

| 项目 | 要求 | 理由 |
|---|---|---|
| 码中心高度 | **1.40–1.65m**（主位建议 1.45m） | 对齐举手机的高度，不弯腰不踮脚 |
| 墙面朝向 | 与通行方向**垂直**，视夹角 ≤30° | ArUco 靠透视变换反解，斜过头 5×5 采样会错 |
| 贴哪面 | 楼梯口出来**抬头第一眼**的那面墙 | 推门即见，不用找 |
| 上下楼错开 | 同一位置上下层的牌**错开 20cm** | 站楼梯中间时上下两张都在视野里，同高度容易串读 |
| 每处几张 | **2 张**（1.45m 主 + 1.65m 备） | 高矮个子都能扫；一张被挡还有另一张 |

### 4.2 印刷与材质

| 项目 | 要求 | 原因 |
|---|---|---|
| 颜色 | 纯黑 K100 + 纯白底 | 对比度不够，二值化会失败 |
| 覆膜 | **哑光**，别用亮膜 | 亮膜一反光，摄像头里就是一片白 |
| ArUco 外框 | **禁止**圆角、花边、渐变、图标 | 会干扰角点检测，直接认不出 |
| 静区 | 纯白，无字无图案，宽度 ≥ 码面 ÷ 7 | 120mm 的码就是左右各 17mm |
| 两个码之间 | 至少留 15mm 纯白 | 防止入口码的模块被误当成 ArUco 的一部分 |
| 材料 | 亚克力 UV 打印 或 PVC 背胶 | 纸质的 3 个月就卷边发黄 |

### 4.3 绝对不要贴的地方

- 门背后、门扇上（一开门就挡住）
- 消防栓、灭火器箱门盖（检修时被遮）
- 开关面板上（有凸起，反光和阴影都糟）
- 强反光瓷砖对面、阳光直射的墙
- 窗户正对面（逆光时码是黑的剪影）
- 洗手间外墙（潮气会让纸翘、让胶失效）
- 低于 1.2m（被书包和人挡）
- 有瓷砖缝、海报、涂鸦的墙（角点被干扰）

### 4.4 每处贴完当场验收（3 分钟）

1. 站牌前 **0.6m**，对准 ArUco，**5 秒内**出「已定位：X层 XX楼梯口」→ 合格
2. 退到 **1.2m** 再试，记录还能不能认 → 这个是余量，不给分但要知道
3. 微信扫下方入口码，看页面能不能正常打开
4. 在表里记一笔（附录 C 有模板）

**不合格就当场挪位置或加大码，别等贴完 100 张再返工。**

## 第五章 116 个码怎么编号（现在改最省）

### 5.1 你现在的 12 个码，用的正好是最容易混的一批

我把 `js-aruco2.js` 的 ARUCO 字典跑了一遍：

- 字典共 **1023 个码**
- 全字典**最小汉明距离只有 3 位**（汉明距离 = 两个码有几个格子不一样）
- 而 **ID 0 和 ID 1 恰好只差 3 位**——它们分别是 3 层的**东北**楼梯口和**西北**楼梯口

这意味着：光线差一点、角度斜一点，只要读错 1–2 个格子，就会把东北认成西北，**人在楼这头、系统以为在楼那头**。而现在 12 个点位用的是 0–11 连续编号，正好把这批最像的码全用上了。

### 5.2 重排后能做到距离 6

我用贪心筛选跑过：从这个字典里挑 **116 个**码，可以让任意两个码至少差 **6 位**（能容忍读错 2 位）。想要 7 位就凑不够 116 个了。

### 5.3 编号规则

1. 按「任意两码至少差 6 位」重筛 116 个 ID
2. **同层相邻点位分到差异最大的码对**——因为它们在同一个走廊，最容易被同框扫到
3. 上下楼同一位置的两个码也要拉开距离
4. 重排后 `data/labs.js` 里 `locations[].marker` 全部要改，**现有 12 张码作废、必须重印**

> 现在改最省。等 116 张都贴上墙再发现问题，就要撕 116 张。

## 第六章 页面要改的 4 处

前两条不修，这套方案等于没做。

| # | 现在 | 改成 | 为什么 | 副作用 |

| 1 | 进页面调 `startCamera(false)`，只开画面不扫描（`:473`） | **定位还没确定时，自动进入扫描状态** | 学生扫完小码进来，举着手机对 ArUco——**现在毫无反应**，会以为坏了 | 一直开相机会耗电、发热 |

## 附录 B · 116 个码怎么来

**总数**：楼梯口 12 + 实验室门牌 104 = 116

**门牌码的数据来源**：`data/labs.js` 的 `labs[]` 里每条都有 `door`（门所在的路点），把 104 条各拆成一个 `locations` 条目即可，不用手工画点：

```
{ "id": "R324", "floor": "B2-3", "node": "B2-3/n3", "marker": <重排后的号>,
  "place": "3层 · 324 实验室门口", "normal": <门的朝向> }
```

### 门牌码有一个精度上限，要先知道

我把 104 条 `labs[].door` 统计了一遍，结果是：

- **81 个房间挤在 30 个门口路点上**，其中最多的一个路点对应 **6 个房间**（如 `B2-3/n2`）
- **30 条记录的门口路点与楼梯口定位点完全重合**（其中 11 条是楼梯间本身，剩下 19 间是普通实验室，例如 324、326、425 的门口都指向 `B2-3/n3`，也就是东北楼梯口）

这意味着扫两张不同门牌的码，系统可能认为你在**完全相同的位置**。

**怎么处理**（三选一）：

| 方案 | 做法 | 精度 | 工作量 |
|---|---|---|---|
| 接受粗定位（推荐先这样） | 门牌码直接复用 `door` 路点 | 同一片区域，误差 1–3 米 | 零 |
| 补路点 | 给 104 扇门在 `nodes` 里各补一个点，`door` 改成新点 | 精确到门前 | 要改数据 + 重新校验连通性 |
| 门牌码只当入口 | 扫了只进站不定位置，定位仍靠楼梯口 ArUco | 取决于楼梯口 | 零，但学生要多扫一次 |

对「我要去别的实验室」这个主用途来说，1–3 米的起点误差影响很小（走过去本来就要重新看箭头）；但如果将来要做「精确定位到门」，得走第二个方案。

**生成命令**（码号重排后执行）：

```bash
python tools/make_aruco.py
```

**注意**：`aruco/print.html` 顶部写着「一页 4 张」，实际 CSS 是一页 1 张、图宽 130mm；`tools/aruco-print.html` 写着「每张 8.5cm」，实际算出来 91mm。**两个提示都不准，以打印后实测为准。**
